# Гарантии и границы проекта

Документ описывает текущее поведение и отдельно отмечает ещё не проверенные
сценарии. Наличие теста подтверждает его сценарий, а не все возможные сбои
и чередования транзакций.

## Транзакции

- Без `BEGIN` каждый SQL-оператор выполняется в отдельной транзакции.
- Внутри `BEGIN` изменения данных, индексов и поддерживаемого DDL фиксируются
  вместе через `COMMIT`; `ROLLBACK` их отменяет.
- Ошибка SQL-оператора внутри блока отменяет транзакцию. До `COMMIT` или
  `ROLLBACK` следующие операторы получают `25P02`; `COMMIT` отвечает `ROLLBACK`.
- READ COMMITTED получает свежий снимок для каждого оператора. При `40001`
  оператор повторяется с откатом его изменений; число попыток ограничено пятью.
- REPEATABLE READ использует один снимок на транзакцию. Конфликт `40001`
  передаётся клиенту: повторять нужно всю транзакцию.
- SERIALIZABLE дополняет снимок блокировками целых таблиц. Эти блокировки
  действуют между SERIALIZABLE-транзакциями; остальные уровни их не берут.
  Это не реализация SSI PostgreSQL. Взаимная блокировка в операторе этого
  уровня переводится в `40001`; ожидание также может завершиться тайм-аутом.

Реализация: `TransactionBlock`, `Catalog.lockSerializable`, `KvTransaction`.
Сценарии проверяются в `TransactionsTest`, `SerializableTest`,
`DdlConcurrencyTest` и `TransactionsOverPgWireTest`.

## Хранение и восстановление

Строки, записи индексов и метаданные хранятся в одной RocksDB. SQL меняет
их через общую транзакцию; успешная запись строки не должна оставлять индекс
в другом состоянии.

| Событие | Текущий статус |
|---|---|
| Закрытие хранилища и повторное открытие | Сохранение данных проверяется `KvStoreTest.dataSurvivesReopen` |
| Откат или закрытие незавершённой транзакции | Отмена изменений проверяется `KvTransactionTest.rollbackAndCloseDiscardChanges` |
| Аварийное завершение JVM через `Runtime.halt` | Вставка, обновление и удаление в подтверждённой транзакции сохраняются, незавершённые изменения исчезают в сценарии `CrashRecoveryTest` |
| Восстановление таблицы и вторичного индекса после `Runtime.halt` | Каталог, строки и обычный вторичный индекс восстанавливаются согласованно в сценарии `CatalogCrashRecoveryTest` |
| Незавершённый DDL перед `Runtime.halt` | В сценариях `CatalogCrashRecoveryTest` созданные без COMMIT таблица и индексы отсутствуют, удалённые без COMMIT таблица и индекс сохраняются вместе с данными |
| Сбой ОС или отключение питания после ответа COMMIT | Сохранение всех подтверждённых транзакций пока не гарантируется проектом |

`KvStore` создаёт `WriteOptions` без явной настройки `sync`. Поэтому успешный
COMMIT сейчас нельзя трактовать как обещание проекта о синхронном сохранении
на устойчивый носитель. Атомарность изменений и их сохранность после потери
питания — разные свойства.

Целевое поведение для следующей проверки: после принудительного завершения
процесса подтверждённые транзакции сохраняются, незавершённые не видны,
таблицы и индексы согласованы. Для транзакции, на которую клиент не получил
ответ, исход может быть неизвестен: потеря ответа не означает откат.
Тест с завершением процесса не подтверждает устойчивость к потере питания.

## Совместимость и ресурсы

Поддерживается часть протокола PostgreSQL для выполнения запросов, включая
подготовленные операторы и текстовые/бинарные значения. Это не обещание полной
совместимости с SQL, системными каталогами или инструментами PostgreSQL.
Основной проверяемый клиент — PostgreSQL JDBC в `swdb-it`.

Аутентификация, TLS и выполнение отмены через CancelRequest пока отсутствуют.
SELECT собирает весь результат в памяти; выдача портала порциями не меняет
этого. Массовый UPDATE и удаление таблицы также собирают данные в памяти.
Ограниченный расход памяти на больших операциях пока не гарантируется.

`CrashRecoveryTest` запускает отдельную JVM и завершает её без `close`,
`finally` и shutdown hooks. Проверка выполняется на уровне ключей хранилища.

`CatalogCrashRecoveryTest` проверяет сохранение описаний таблицы и индекса,
подтверждённых вставки, обновления и удаления строк и отсутствие незавершённых
изменений. Полный проход таблицы сравнивается с проходом вторичного индекса;
точечные диапазоны проверяют новые, старые и незавершённые значения индекса,
включая одинаковое значение у нескольких строк. SQL и сетевой протокол
в этих сценариях не участвуют.

Два дополнительных сценария проверяют незавершённый DDL: создание таблицы
с данными и индексом и создание индекса на существующей таблице; отдельное
удаление индекса и удаление другой таблицы вместе с её индексом. После аварии
проверяются имена объектов, описания таблиц и чтение сохранённых данных
напрямую и через индекс. Авария происходит после выполнения DDL до COMMIT;
прерывание в середине COMMIT этим не проверяется.

Следующий небольшой шаг: проверить восстановление уникального индекса и
сохранение проверки уникальности после аварии процесса.
