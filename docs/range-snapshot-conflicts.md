# Диапазоны и конфликты со снимком

Это план реализации, а не описание уже действующих гарантий.
SQL пока использует блокировку всей таблицы через SerializableLocks.

## Зачем нужна история

А получила снимок №100. Б изменила ключ 15, сделала COMMIT и сняла блокировку.
Затем А запросила чтение диапазона от 10 включительно до 20 исключительно.
Ожидать уже некого, но снимок А устарел относительно записи Б.
Нужна ошибка 40001, как при нынешней проверке служебного ключа таблицы.

У диапазона есть две разные защиты:

- Активная блокировка не допускает несовместимую работу других владельцев.
- История завершённых записей обнаруживает изменения после снимка.

## Какие сведения хранить

У одного KvStore будет общий учёт:

- Номер снимка каждого живого владельца транзакции.
- Диапазоны успешно зафиксированных записей и номер их фиксации.
- Уже существующие активные блокировки и запросы ожидания.

Используем номера RocksDB. В исходниках зависимости rocksdbjni 11.1.2
проверены Snapshot.getSequenceNumber и RocksDB.getLatestSequenceNumber.
Собственный счётчик COMMIT не вводим: его пришлось бы согласовывать
с созданием настоящих снимков RocksDB.

Для первой реализации можно сохранять все EXCLUSIVE-диапазоны успешной
пишущей транзакции. Это консервативно: защищённый диапазон может быть шире
фактически изменённых ключей. Позже можно учитывать точные записи.
Режим EXCLUSIVE сам по себе не доказывает, что данные были изменены.

## Порядок операций

1. BEGIN создаёт снимок и регистрирует его номер под тем же монитором,
   который защищает очистку истории. Регистрируем все транзакции заранее:
   первая блокировка диапазона может понадобиться значительно позже BEGIN.
2. Захват диапазона сначала разрешает конфликты активных блокировок,
   включая ожидание и обнаружение циклов. Затем под тем же монитором
   проверяет историю. Пересечение с записью новее снимка даёт 40001.
   Проверка применяется и к чтению, и к записи, до доступа к данным.
3. COMMIT выполняет фиксацию в RocksDB, продолжая удерживать диапазоны.
   Нельзя удерживать монитор менеджера во время вызова RocksDB COMMIT:
   остальным владельцам нужен доступ к менеджеру для завершения.
4. После успешного COMMIT получаем текущий номер изменений RocksDB.
   Это верхняя оценка номера нашей фиксации: параллельная запись могла
   уже увеличить его. Завышение допускает лишний конфликт, но не пропуск.
5. Под монитором публикуем историю, снимаем блокировки и регистрацию
   снимка, очищаем ненужную историю и будим ожидающие потоки.
   Все эти изменения должны быть одной операцией менеджера.
6. ROLLBACK не публикует записи. После успешного отката снимает блокировки
   и регистрацию снимка. Close завершает освобождение ресурсов, в том числе
   после ошибки COMMIT; успешную фиксацию нельзя подменять простым releaseAll.

Пока писатель не опубликовал историю, его EXCLUSIVE-блокировки остаются.
Читатель пересекающегося диапазона не должен пройти между COMMIT и публикацией.
Новый снимок нельзя создать вне монитора и зарегистрировать позже:
за этот промежуток нужная ему история могла бы быть удалена.

READ COMMITTED обновляет снимок и его регистрацию согласованно с очисткой.
Для первой реализации откат к точке сохранения продолжает удерживать диапазоны;
их консервативный учёт не должен потерять защиту ранее прочитанных данных.

## Когда очищать историю

Пусть самый старый зарегистрированный снимок имеет номер S. Записи истории
с номером не больше S больше не нужны: ни для одного живого снимка они
не являются более новыми. Если живых снимков нет, историю можно очистить целиком.
Долгая транзакция задерживает очистку; произвольный лимит с удалением нужной
истории недопустим. Политику ограничения таких транзакций добавим отдельно.

История живёт в памяти. После перезапуска старых транзакций и их снимков
уже нет, поэтому восстанавливать эту историю с диска не требуется.

## Условия перед подключением к SQL

Все участники диапазонного SERIALIZABLE должны захватывать диапазоны до
операций и удерживать их до завершения. Один LockRange не обеспечивает изоляцию.
Прямые KvStore.put/delete/write пока обходят диапазонный протокол.
Их нельзя незаметно включать в обещание этой проверки. Другие уровни изоляции
пока сохраняют прежние правила; общую сериализуемость смешанных уровней не обещаем.

Первичный ключ и индекс имеют разные физические диапазоны. При изменении строки
нужно защищать ключ строки и старые/новые ключи затронутых индексов. Чтение через
индекс должно защищать диапазон индекса, включая места ещё отсутствующих строк.
Переход начнём с первичного ключа и безопасной блокировки всей таблицы
для остальных путей, не заменяя существующую защиту частично.

Менеджер пока видит циклы только среди диапазонов, а RocksDB — среди своих
ключевых блокировок. До перехода SQL нужно определить единый порядок захвата
или объединённый учёт ожиданий. Текущий тайм-аут ограничивает ожидание,
но не заменяет обнаружение цикла между двумя механизмами.

## Небольшие шаги реализации

1. Отдельный учёт снимков и истории: проверка пересечения и правила очистки.
2. Согласовать BEGIN, refreshSnapshot, COMMIT и ROLLBACK с этим учётом.
3. Включить проверку истории при захвате диапазонов на уровне хранения.
4. Решить порядок взаимодействия с ключевыми и DDL-блокировками.
5. Подключать пути SQL по одному, начиная с первичного ключа.
